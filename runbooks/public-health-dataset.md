# Runbook: public health dataset

The dataset in `deliverables/public-health-dataset/` is written by `export_public_health_dataset.py` and checked by `python3 -m lovs.snapshot_contract --check-dataset`, which `release_snapshot.py --check` runs. Each row starts from the message a maintainer sees. The rows cover the metric, geography and provenance checks; other `--check-dataset` messages (snapshot headline, corridors, claim audit, gaps and per-zone checks) name the file, row, claim or limitation and the disagreement, and are fixed by regenerating from the same promotion or reviewing that promotion. Never change a value to make a check pass: every fix below changes a label, a classification or a regeneration. When a source itself prints two different figures for one thing, stop and ask the dataset owner before choosing one.

## Export

| Message | Check | Fix |
|---|---|---|
| "source field 'X' names a case class but is not in the public dataset's metric vocabulary" (prefixed with the source id) | Read field X in the newest reviewed promotion and in `data/bundibugyo-2026/manifest.json`. | Classify X in `export_public_health_dataset.py`: `CUMULATIVE_METRIC_BY_FIELD` for a running total, `DAILY_METRIC_BY_FIELD` for a 24-hour count, `CASELOAD_METRIC_BY_FIELD` for a count on the report date, or `OWN_NAME_CASE_FIELDS` to keep its own name. A new two-country total also goes in `COUNTRY_SCOPE_TOTAL_KEYS`. A new case field whose name names no country, on a source covering both countries, then needs a reviewed geography unless it is a country-scope total (see the gate row "is an unqualified ..."). A new metric name goes in `CUMULATIVE_SOURCE_METRICS` or `DAILY_SOURCE_METRICS` in `lovs/snapshot_contract.py` too. If the field's name uses a country or province word the dataset does not know, add the word to `_COUNTRY_BY_FIELD_TOKEN` there. Add a test, then rerun the release check. |

## Dataset gate (`--check-dataset`)

| Message | Check | Fix |
|---|---|---|
| "a source gives each cumulative series one value" | The message names both rows. A cumulative metric at `COD; UGA` is the same series as its `country_scope_` metric. | Usually a DRC term and a two-country term are filed together: fix the field's geography (`_COUNTRY_BY_FIELD_TOKEN`, `COUNTRY_SCOPE_TOTAL_KEYS`) or add a reviewed label with the source's evidence to `REVIEWED_SOURCE_FIELD_LABELS` in `lovs/snapshot_contract.py`. Then regenerate with `python3 export_public_health_dataset.py` then `python3 -m lovs.public_exports`. If you added a label, update the pinned counts in `tests/test_public_health_export.py` (`test_reviewed_labels_move_may_drc_figures_out_of_the_two_country_series`), or the release check's test step fails. |
| "a source gives each 24-hour series one value" | Two fields of one source feed one 24-hour metric with different values (for example `new_confirmed_deaths_24h` and `total_confirmed_deaths_24h`). | If the two numbers are different measures, stop and ask. If one SitRep printed a wrong copy, give that source's other field a reviewed label (`location` plus `metric` set to the field's own name) in `REVIEWED_SOURCE_FIELD_LABELS`, quoting the source. Do not move a field out of `DAILY_METRIC_BY_FIELD` for one SitRep: that relabels every earlier SitRep that uses it (SR099 onward for `total_confirmed_deaths_24h`) and needs `OWN_NAME_CASE_FIELDS` as well. Then regenerate with `python3 export_public_health_dataset.py` then `python3 -m lovs.public_exports`. Then update the pinned counts in `tests/test_public_health_export.py` (`test_reviewed_labels_move_may_drc_figures_out_of_the_two_country_series`), or the release check's test step fails. |
| "is an unqualified ... from a source covering more than one country; read the source and record whether it is the DRC figure ('COD') or the two-country figure ('COD; UGA')" | Read the source's text around the figure: does it cover DRC only (a DRC paragraph, a DRC province or health zones, the total minus Uganda's figure) or both countries? The gate finds these counts by field name (a case word and no country; country-scope totals are placed by their own rule), so when adding a two-country source also read any count whose field has no case word (for example `officially_reported_at_that_date`) and decide it the same way. A CDC current-situation capture in the DRC/Uganda split format writes bare `cases_confirmed` (DRC plus Uganda) and bare copies of the DRC suspected terms. | Add a `REVIEWED_SOURCE_FIELD_LABELS` entry with `COD` or `COD; UGA` and a comment quoting the source. If the figure is a different measure (for example deaths among suspected cases), also give `metric`. If the value matches no count for its geography, keep the field's own name as `metric` and add a `note`; never change the value. Then regenerate with `python3 export_public_health_dataset.py` then `python3 -m lovs.public_exports`. Then update the pinned counts in `tests/test_public_health_export.py` (`test_reviewed_labels_move_may_drc_figures_out_of_the_two_country_series`), or the release check's test step fails. |
| "but its reviewed label in REVIEWED_SOURCE_FIELD_LABELS is" | The export did not apply a reviewed label, or the label no longer fits. | Regenerate with `python3 export_public_health_dataset.py` then `python3 -m lovs.public_exports`. If the source changed, update the label and its evidence. |
| Importing `lovs.snapshot_contract` fails: "reviewed label ... must give location 'COD', 'UGA' or 'COD; UGA'" | A table entry has no `location`, an unknown one, or a key other than `metric` and `note`. | Give every entry a `location`; a metric-only label is not allowed. |
| "is the two-country metric ... it must sit at 'COD; UGA'" or "location=...; a country-scope row must be ..." | A `country_scope_` metric or field is labelled with one country. | Two causes. A genuine two-country total that the export placed at one country: add the field to `COUNTRY_SCOPE_TOTAL_KEYS` in `export_public_health_dataset.py`. A DRC or Uganda term classified as a country-scope total: move it to `confirmed_cases`, `deaths` or its own name. |
| "... but the contract's ... term is ..." or "lacks the contract's country-scope composition rows" | The latest SitRep's total, DRC and Uganda terms disagree with `data/snapshot_contract.json`. | Rerun `python3 release_snapshot.py --check --as-of <data date>`, which regenerates the contract and the dataset from the same promotion; if they still disagree, the promotion needs review. |
| "is exported as the cumulative ..., but a cumulative series takes only a top-level ... count field" | A nested, increment, caseload, rate or other-class field joined a cumulative series. | Move the field out of `CUMULATIVE_METRIC_BY_FIELD`. |
| "is a percentage field but has unit" or "is a death source metric but exported as" | A unit or metric contradicts the field's own name. | Add the field to `UNIT_BY_FIELD`, or classify it under a death metric. |
| "timeline.csv ... has ... but reported_counts.csv has ..." | The two files were written by different exports. | Regenerate both with `python3 export_public_health_dataset.py` then `python3 -m lovs.public_exports`. |
| "package manifest records <input> as sha256 ... but the file is ..." or "package manifest input ... is not in the repo" | An input changed after the export, or was left out of the commit. `data/live-bdbv-2026-output.json` carries a wall-clock date, so a release check run on a later day rewrites it. | Commit the regenerated input together with the dataset, or restore the committed input and rerun `python3 export_public_health_dataset.py` and `python3 -m lovs.public_exports` before committing. |
| "lovs-public-health-dataset.manifest.json is missing" | The export did not finish. | Rerun `python3 export_public_health_dataset.py`. |

## Committed files against a rebuild

CI runs `python3 export_public_health_dataset.py --check`, which exports into a temporary directory from the committed inputs and byte-compares every file with `deliverables/public-health-dataset/`, and `python3 -m lovs.public_exports --check`. Never edit a generated file by hand to make either pass.

| Message | Check | Fix |
|---|---|---|
| "<file>: differs from a rebuild of the committed inputs" | The committed file is not what the export writes from the committed inputs: a hand edit, an export run before an input changed, or an input changed and committed without its export. | Rerun `python3 export_public_health_dataset.py` then `python3 -m lovs.public_exports`, and commit the inputs and the dataset together. If the regenerated diff shows values you did not expect, review the input change. |
| "...xlsx: differs ...; its unpacked contents match the rebuild, so the difference is in the zip encoding (this interpreter's zlib is ...)" | Every workbook member matches the rebuild; the zip bytes do not. Either this machine's zlib deflates differently from the one that wrote the workbook (stock zlib 1.2.12, 1.2.13 and 1.3.2 were tested and give the same bytes; zlib-ng does not), or the workbook was recompressed or its zip data changed outside the export. The manifest line that comes with it follows from the workbook's hash. | Run the check on a machine with stock zlib (`python3 -c "import zlib; print(zlib.ZLIB_RUNTIME_VERSION)"`). If it passes there, this machine's zlib is the cause: do not regenerate here, since that would commit its deflate bytes, and if this machine is the CI runner, ask the dataset owner. If it fails there too, regenerate as above. |
| "<file>: is a symbolic link, but the export writes a regular file" | A dataset file was replaced by a link. The export writes through a link, into its target. | Delete the link itself (not its target), then regenerate as above. |
| "<file>: missing, but the export writes it" or "<file>: present, but the export does not write it" | A file was deleted from, or added to, the dataset directory by hand. The directory holds only what the export writes. | Regenerate as above, and remove any file the export does not write. |
| "data/public_export_source.json: differs from what --sanitize-source writes from the snapshot" | The text artifacts are rebuilt from this file, so an edit to it, or a snapshot change without a new sanitize, passes as current. | Rerun `python3 -m lovs.public_exports --sanitize-source` then `python3 -m lovs.public_exports`. Never edit the export source by hand. |

## Versions

Keep the package manifest's `schema_version` at 2: `lovs/semantic_freshness_gate.py` enforces its per-artifact checks only for that value. Version the dataset's content through `lovs-public-health-dataset.schema.json`, and describe every vocabulary change in `CHANGELOG_MD` (`lovs/public_exports.py`) with counts recomputed at the final regeneration.
